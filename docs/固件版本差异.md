# 固件版本差异（2026-11-27 发现，高度可疑的根因）

> **一句话：我们的相机固件是 `30110_06.2026060501`，上游只验证过 `30110_05.2025031501`。
> 上游自己的文档写着"协议依赖版本"。**

---

## 一、上游文档的原话

`dino2048/zv-e10-toolkit` 的 `fastboot/pico/PROTOCOL.md`：

> 2026-10-22 在本机实测成功。本文是与当前可用方案配套的协议摘要；
> 详细逆向记录不在本发布仓库内。

`linux/docs/service-mode.md`：

> The protocol is undocumented and **version-dependent**.
> **Only `30110_05.2025031501` on the ZV-E10 is tested.**

---

## 二、我们这台相机的固件版本

**从 Sony 官方固件包 `firmware.fdat` 里检索到的版本串：**

```
偏移 0x26240:  30110_06.2026060501
```

**对应关系：**

| 字段 | 含义 |
|---|---|
| `30110` | ZV-E10 机型代码 |
| **`_06`** | **固件大版本** |
| `2026060501` | 构建日期 2026-06-05 |

**上游验证的是 `_05`（2025-03-15），我们的是 `_06`（2026-06-05）—— 差一个大版本、一年零三个月。**

> ⚠️ **重要限制**：`firmware.fdat` 是**下载的升级包**，理论上等于相机可用的最新固件，
> **但不保证等于相机里正在运行的那个版本**。要确认实际版本需要读相机
> （而用户态已死，读不到）。这一点是本次推论最大的不确定性。

---

## 三、为什么这个假设能一次解释所有阴性结果

| 我们观察到的 | 用"新固件关闭了 BootROM 串口启动"解释 |
|---|---|
| 接线全部正确（逐点电压、压降、CC 双下拉都验过） | 对，但门关了 |
| 波形纳秒级精确（60×250µs / 125µs / 20.833µs） | 对，但 ROM 不采样 |
| 官方 payload，sha256 与上游一致 | 对，但没人接 |
| 参数用上游官方值（record-gap 2ms / reset-delay 100ms） | 对 |
| **垃圾方波不报 `0x100D`（13 短闪）** | **ROM 根本没在听这根线** |
| **完整 payload 不报 `0x2002/0x2003/0x2004` 任何错误码** | 同上 |
| **USB 身份判据：换普通数据线后只有 `054c:0994`，没有 `ZVE10-fastboot`** | 同上 |
| 反插 180°（等价 B7/B6）也无反应 | 同上 |

**关键点：如果 ROM 在采样这根线但记录内容不对，它必然报错误码
（`0x2002` token 错 / `0x2003` CRC 错 / `0x2004` 记录不完整）。**

**我们拿到的是彻底的沉默——连错误码都没有。这说明 ROM 从未进入串口接收模式。**

## 四、还能怎么验证这个假设

### 4.1 查 token 是否随版本变化（已做，无结论）

`PROTOCOL.md` 说 token 来自**相机自己的 boot0（EXBL 头）偏移 `0x200` 的 8 字节**：

```
V = 0x8CB102DC
C = 0xA86DA25E
crc32(V || C) == 0xFFFFFFFF
```

**如果固件换版，token 大概率也换。** 我在 `firmware.fdat` 里全文检索了 `V` 的小端表示
（`dc 02 b1 8c`）以及 `V+C` 相邻形式：

```
V (LE) occurrences: 0
V+C adjacent:      0
```

**没找到。**

**怎么解读这个"没找到"（两种都可能，不要过度解读）：**

- **可能 A**：`firmware.fdat` 是**升级包**，里面的 boot0/EXBL 可能是加密或压缩的，
  所以明文 token 搜不到——**这不代表 token 变了**
- **可能 B**：token 确实随版本变了——**但那样也会报 `0x2002`，而我们是沉默**

**所以这个检索没有区分力，不能作为证据。** 它只说明"我们无法从升级包里确认 token"。

### 4.2 向开发者提问（已发）

- **dino2048**（toolkit 作者，真机成功过）：
  「你成功时相机跑的是哪个固件版本？如果当时是 `_05` 而我这台是 `_06`，那就能解释我所有的阴性结果。」
  → [issue #8 comment](https://github.com/dino2048/zv-e10-toolkit/issues/8#issuecomment-7220518303)
- **DavidBuchanan314**（串口 boot 逆向原作者）：
  「串口启动的门是纯 boot strap/ROM 代码决定，还是可以被固件关闭
  （烧 eFuse / boot header 标志 / 从 boot0 打 ROM patch）？」
  → [ILCE-7M4-RE#3 comment](https://github.com/DavidBuchanan314/ILCE-7M4-RE/issues/3#issuecomment-7220520761)

### 4.3 我们还能自己做的事

| 做法 | 可行性 | 说明 |
|---|---|---|
| 找 `_05` 的老固件包比对 | **低** | Sony 官网只提供最新版；旧版几乎找不到 |
| 从 `firmware.fdat` 里解出 boot0/EXBL 看明文 token | 中 | 需要先搞清 fdat 的封装格式（magic `UDTRFIRM`） |
| 确认相机里实际跑的版本 | **不可行** | 用户态已死，读不到任何系统信息 |

## 五、这个假设对结论的影响

**如果假设成立：**

- **用户没有做错任何事。** 接线、波形、payload、参数全部正确。
- **"上游能做我不能做"不是矛盾**——差别在固件版本，不在硬件或操作。
- **而且这意味着：买 Pico 也没用。** 发送端再精确，改变不了 ROM 不采样的现实。
  （省下这笔钱。）

**如果假设不成立（相机里其实是 `_05`）：**

- 那问题回到"物理入口"，只有点位图或拆机能解决。
